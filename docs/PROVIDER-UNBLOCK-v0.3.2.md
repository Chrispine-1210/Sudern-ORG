# Provider actions required before SUDERN release certification

These are account-level operations that **were not executed** by the connected tools. Never paste secrets into issues, pull requests or chats.

1. **Vercel Marketplace → Neon:** From the correct Vercel team, create a **new Neon Postgres** resource named `sudern-ops` and connect it to the existing `sudern-institutional-ops-preview` project (protected all deployments). The connected Neon project API refuses `create_project` on the Vercel-managed organisation. The Vercel connector currently exposes no marketplace database resource-creation operation. Do not borrow a Mtendere, Aöthothe, portfolio or pharmacy database. Record the newly created managed resource/project ID.
2. **Isolation:** Create an independent disposable `sudern_test` or `sudern_sandbox` PostgreSQL database (prefer separate managed branch). Provision distinct limited runtime and migration roles, keep Preview distinct from future Production. The test script validates the database name and existing rows and refuses nonempty datasets; verify this before running anything destructive.
3. **Private GitHub repo:** Create `sudern-institutional-ops` under the intended authorised owner. From the delivered Git bundle, clone and push to the newly created remote without leaking `.env`, `.db`, `.sqlite` or SQL dump. Set branch protection to require actual `static-and-legacy` and `isolated-postgres` checks, not placeholder statuses; protect `main` and maintain exact commit evidence.
4. **Dependency lock:** In a trusted networked build environment run `npm install --package-lock-only --ignore-scripts --no-audit --no-fund`, inspect the resolved dependency graph, commit the resulting *real* `package-lock.json`, and require `npm ci` on every CI run. This produces a new Git SHA; tie deployment and certification to the **new** SHA, never the older local source commit.
5. **Secrets:** Configure encrypted Preview variables `DATABASE_URL` (dedicated managed branch), `MFA_ENCRYPTION_KEY` (32-byte cryptographic key in canonical base64), `SANDBOX=true`, `INTAKE_ENABLED=false`, `SUDERN_PRODUCTION_AUTHORIZED=false`. Never expose any secret in workflow logs or PR comments. Confirm the connection points at the right isolated branch.
6. **CI and database:** Run PostgreSQL migration v1→v2 on the empty isolated branch, then `npm run verify:postgres`, `npm run test:postgres`. The GitHub Actions workflow should execute PostgreSQL 17 full synthetic journey, concurrent expense allocation denial and encrypted empty-target restore; capture exact head/run IDs and sanitized logs.
7. **Preview:** Deploy the exact committed application to the already protected Vercel project. Keep custom Production domains unassigned and public intake disabled. Capture actual deployment ID and verify commit SHA and `/api/health` schema v2. Set protected CI environment `sudern-preview-approval` with synthetic staff credentials and expected URL; run `npm run preview:smoke`. Exercise browser journeys and role/RBAC/CSRF flows against **managed Postgres**, not local SQLite.
8. **Managed restore:** Separately execute encrypted backup to a new empty **managed** PostgreSQL restore target, verify all data counts, audit tip, application login/readback and documented cleanup. The CI container restore alone is insufficient evidence of managed restore readiness.
9. **Executive decision:** Complete NGO legal/regulatory and organisational sign-off, approved privacy/retention/safeguarding policies, governance authority, bank/funding policy, production monitoring, recovery drills and independent security review. Only then consider a narrowly scoped, accountable production GO.
